# SEO и публикация «Дом Зубов»

## Текущее состояние

SEO подготовлено для 56 действующих страниц: главной, 40 услуг и 15 информационных страниц. Публичный домен ещё не подтверждён. По умолчанию сайт остаётся закрыт для индексации; эта работа сама по себе не публикует сайт и не включает индексирование.

`app/seo.php` хранит отдельные заголовки и описания страниц, список канонических маршрутов, JSON-LD и генераторы XML sitemap и robots.txt. Архивный `content/routes.json` не является списком для sitemap. Старые врачи, акции, документы, старые клиники, редиректы, поиск и URL с параметрами в XML-карту не включаются. Новые действующие страницы необходимо явно добавить в SEO-реестр; для новой услуги также добавить описание в `dz_seo_service_descriptions()`.

## Настройки сервера

В `app/site-config.php` используются две переменные окружения:

| Переменная | Значение и поведение |
| --- | --- |
| `DZ_SITE_URL` | Подтверждённый основной адрес вида `https://домен` (международные домены — в ASCII/Punycode). Только `http` или `https`, имя хоста и необязательный порт. Путь, логин, пароль, query и fragment запрещены. Конечный `/` нормализуется. |
| `DZ_ALLOW_INDEXING` | Только точная строка `1` разрешает индексирование. Отсутствие, `0` и другие значения оставляют его выключенным. |

Некорректный или отсутствующий `DZ_SITE_URL` даёт безопасное значение `http://127.0.0.1:8174` и запрещает индексирование. Для localhost, локальных имён, тестовых доменов и IP-адресов индексирование не включается даже при `DZ_ALLOW_INDEXING=1`. Публичному сайту нужен подтверждённый DNS-домен. Заголовки `Host`, `Forwarded`, `X-Forwarded-Host` и `REQUEST_URI` не определяют canonical, sitemap, social URL или идентификаторы schema.org. Изменение этих переменных может потребовать перезапуска PHP-процесса на хостинге.

Пока индексирование выключено, страницы получают `noindex, nofollow`, а robots.txt — `Disallow: /` без ссылки на sitemap. После включения robots.txt разрешает обход и указывает sitemap на настроенном домене. Поиск, неизвестные и архивные страницы вне реестра всегда имеют `noindex, nofollow`; им не назначаются canonical и JSON-LD. Поиск специально не закрыт отдельным `Disallow`, чтобы поисковик мог прочесть его `noindex` после запуска.

`Disallow` ограничивает обход, но не гарантирует удаление уже известных URL из поиска. Если тестовый сайт уже попал в индекс, поисковому роботу необходимо дать увидеть `noindex`; для срочного удаления используют инструменты соответствующей поисковой системы. На публичном стенде доступ ограничивают средствами хостинга: robots.txt и метатеги не защищают данные. [Документация Google о noindex](https://developers.google.com/search/docs/crawling-indexing/block-indexing).

## Подключение в PHP

После `app/bootstrap.php` подключается `app/seo.php`. Перед шаблоном header:

```php
$seo = dz_seo_prepare($route, $page, $service, $editorial);
```

`templates/seo-head.php` выводится внутри `<head>` вместо прежних title, description и robots. Он экранирует HTML-атрибуты; `dz_seo_json()` экранирует опасные для HTML символы JSON-LD. SEO-данные берутся из собственного реестра, а не из пользовательских запросов или импортированных заголовков. Для поисковых и ошибочных страниц запрос пользователя не отражается в метаданных.

`dz_seo_sitemap_xml()` возвращает XML для `/sitemap.xml`; обработчик должен отправлять `Content-Type: application/xml; charset=UTF-8`. `dz_seo_robots()` возвращает текст для `/robots.txt`; его тип — `text/plain; charset=UTF-8`. Маршрутизатор и веб-сервер должны направлять эти два адреса в соответствующие обработчики, а не отдавать старые статические файлы. В режиме стенда XML-карта доступна для проверки, но robots.txt её не рекламирует.

Canonical, `og:url`, sitemap и schema.org используют один основной адрес без параметров. У XML-карты намеренно нет вымышленных дат `lastmod`, приоритетов или частоты обновления. [Canonical в Google](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls), [правила sitemap](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap).

## Содержание schema.org и социальных карточек

Каждая каноническая страница содержит связанные сущности `Organization`, `WebSite`, `WebPage` и один `Place` для фактических адресов приёма. На внутренних страницах добавляется `BreadcrumbList` минимум с двумя элементами. На страницах услуг добавляется `Service` со ссылкой на собственную организацию как провайдера. Телефон и email берутся из `app/company.php`; там же находятся адреса. Юридическое название соответствует реквизитам на странице документов.

Используется общий тип `Organization`: медицинская лицензия и полный комплект документов пока не подтверждены. Адрес описан как место приёма, без утверждений о владении принимающими клиниками, без неподтверждённых часов работы или координат. После проверки сведений можно отдельно уточнить тип организации и данные лицензии.

Разметка не содержит `Review`, `AggregateRating`, `Offer`, вымышленных специалистов, гарантии результата, утверждённого прейскуранта или доступности услуг по записи. Предварительные цены и предоставленные тексты отзывов не превращаются в коммерческие предложения и рейтинг. Не размечаются демонстрационные клинические истории как доказанные результаты лечения.

Для Open Graph и Twitter используется собственная локальная иллюстрация `assets/images/reception.webp`. В описании изображения явно указано, что это иллюстрация, а не документальная фотография клиники. Изображение не используется как подтверждение клинического результата и не скачивается с внешнего сервиса.

JSON-LD помогает описать страницу, но не гарантирует индексацию, позиции или расширенный результат. Тип `Service` не означает, что Google покажет отдельную расширенную карточку услуги. [Требования Google к структурированным данным](https://developers.google.com/search/docs/appearance/structured-data/sd-policies), [Organization](https://schema.org/Organization), [Service](https://schema.org/Service), [Place](https://schema.org/Place), [BreadcrumbList](https://schema.org/BreadcrumbList).

## Перед разрешением индексации

1. Подтвердить основной домен, HTTPS и единый вариант хоста; настроить постоянные редиректы альтернативных адресов средствами хостинга.
2. Согласовать опубликованные сведения о лицензии, медицинских работниках, ценах и юридические документы. Уточнить условия ДМС, сертификатов и программ. Проверить права и согласия для отзывов и будущих фотографий.
3. На хостинге задать правильный `DZ_SITE_URL`, оставив `DZ_ALLOW_INDEXING=0` на время проверки.
4. Проверить HTTP-ответы, один canonical на страницу, отсутствие старого домена, сохранность редиректов, JSON-LD и социальное изображение. Убедиться, что `/sitemap.xml` содержит только действующие страницы с ответом 200.
5. После решения владельца о публикации задать `DZ_ALLOW_INDEXING=1`. Проверить согласованность robots meta и HTTP `X-Robots-Tag`, отсутствие оставшегося общего `noindex` в конфигурации хостинга и доступность CSS, JavaScript и изображений для роботов. Поиск и ошибки должны сохранять `noindex`.
6. Проверить опубликованные страницы через [Schema.org Validator](https://validator.schema.org/) и [Google Rich Results Test](https://search.google.com/test/rich-results). Добавить сайт и sitemap в Google Search Console и Яндекс Вебмастер. Отсутствие поддерживаемого расширенного результата для `Service` само по себе не означает ошибку JSON-LD.

## Автоматическая проверка

Из корня проекта:

```powershell
C:/php/php.exe tests/seo-unit.php
```

Тест проверяет уникальные title/description/canonical всех 56 страниц, лимиты длины, структуру JSON-LD, собственные контакты, связь услуг с организацией, XML, robots, экранирование HTML/JSON и защиту домена от пользовательских заголовков. Отдельно проверяются некорректные значения домена, локальные адреса и переключение режима индексации. Это локальная проверка кода; она не заменяет проверку ответов настоящего веб-сервера после настройки домена.
